# 量化交易系统设计方案

> 目标：设计一个可从研究、回测、模拟盘逐步演进到小规模实盘的量化交易系统。  
> 适用范围：中低频股票 / ETF / 期货 / 加密资产策略。  
> 不适用范围：微秒级高频交易、撮合所托管机房、FPGA、跨交易所低延迟套利。

---

## 1. Executive summary

推荐采用 **模块化单体 + 独立数据管道 + 可替换交易网关** 的架构起步。

核心理由：

- 量化系统早期最大的风险不是吞吐，而是 **数据错误、回测失真、风控缺失、实盘执行偏差**。
- 研究、回测、模拟盘、实盘必须共用同一套策略接口和风控模型，否则很容易出现“回测能跑、实盘失真”。
- 不建议一开始拆成大量微服务；交易系统的复杂度主要来自一致性、时序、风控和审计，不来自 API 数量。

推荐架构分层：

```text
数据层 → 研究层 → 策略层 → 风控层 → 交易执行层 → 账户与绩效层 → 监控运维层
```

第一阶段只做：

- 行情 / 财务数据接入；
- 策略研究与回测；
- 模拟盘；
- 单账户实盘；
- 基础风控；
- 全链路日志与审计。

等到策略数量、账户数量、交易频率或团队边界真的扩大，再拆服务。

## 2. Scope, assumptions, and open questions

### 2.1 范围

本方案覆盖：

- 数据采集与存储；
- 因子和信号计算；
- 策略研究和回测；
- 模拟盘；
- 实盘交易；
- 风控；
- 订单管理；
- 持仓和资金核算；
- 绩效归因；
- 监控、报警和审计。

暂不覆盖：

- 高频交易低延迟优化；
- 自建撮合系统；
- 复杂多租户资管平台；
- 面向外部客户的交易 SaaS；
- 合规报送系统；
- 大规模机器学习训练平台。

### 2.2 假设

| 项目 | 假设 |
|---|---|
| 交易频率 | 日频、分钟级、低频事件驱动为主 |
| 策略数量 | 初期 1-20 个策略 |
| 账户数量 | 初期 1-10 个账户 |
| 标的数量 | 100-10000 个标的 |
| 数据规模 | 日线 / 分钟线为主，Tick 数据可后续扩展 |
| 延迟要求 | 秒级到分钟级，不追求微秒级 |
| 资金规模 | 小到中等规模，先验证系统稳定性 |
| 团队规模 | 1-5 人研发 / 研究小团队 |
| 部署方式 | 单机或小型云服务器起步，后续容器化 |

### 2.3 开放问题

1. 交易市场：A 股、美股、期货、加密资产，还是多市场？
2. 是否需要实盘自动下单，还是只做研究和模拟盘？
3. 是否有监管、审计、权限隔离要求？
4. 目标延迟：日频、分钟级、秒级，还是高频？
5. 数据源是否已有：AkShare、Tushare、Wind、交易所、券商、Yahoo Finance？
6. 是否多账户、多策略共享资金池？
7. 是否需要 Web UI？还是命令行 + 报告即可？

## 3. Architecture drivers

### 3.1 Functional requirements

| 编号 | 功能需求 |
|---|---|
| FR1 | 接入行情、财务、宏观、公告等数据 |
| FR2 | 对原始数据做清洗、复权、对齐、版本管理 |
| FR3 | 支持因子计算、信号生成、策略研究 |
| FR4 | 支持历史回测，输出收益、回撤、夏普、换手、交易明细 |
| FR5 | 支持模拟盘，按实时或准实时数据运行策略 |
| FR6 | 支持实盘下单、撤单、订单状态同步 |
| FR7 | 支持账户、资金、持仓、成交、委托管理 |
| FR8 | 支持事前、事中、事后风控 |
| FR9 | 支持策略配置、启停、版本记录 |
| FR10 | 支持日志、指标、报警、审计和复盘报告 |

### 3.2 Non-functional requirements

| 质量属性 | 目标 |
|---|---|
| 正确性 | 数据、回测、持仓和成交必须可追溯、可复算 |
| 安全性 | 交易密钥加密存储，最小权限访问，敏感日志脱敏 |
| 可恢复性 | 进程重启后可从持久化状态恢复策略、订单和持仓 |
| 可观测性 | 每个信号、订单、成交、风控拒绝都有日志和追踪 ID |
| 可测试性 | 策略逻辑可用同一接口跑单元测试、回测、模拟盘和实盘 |
| 可扩展性 | 后续可增加新数据源、新券商、新策略、新市场 |
| 成本 | 初期避免过度基础设施，优先本地 / 单机 / 托管数据库 |
| 风控优先 | 风控失败时默认拒单，而不是放行 |

### 3.3 Ranked quality scenarios

| 优先级 | 场景 | 响应目标 |
|---|---|---|
| P0 | 实盘下单前触发仓位超限 | 风控拒单，记录原因，不发送到券商 |
| P0 | 交易进程重启 | 从订单表、成交表、持仓快照恢复，不重复下单 |
| P0 | 数据源返回异常价格 | 数据校验失败，不进入策略计算，报警 |
| P0 | 券商 API 超时 | 不无限重试；订单状态进入 unknown，启动对账 |
| P1 | 回测结果复现 | 同一代码版本、数据版本、配置版本可复现结果 |
| P1 | 策略异常 | 单策略熔断，不影响其他策略和账户核算 |
| P1 | 日终对账 | 系统持仓与券商持仓差异必须输出并报警 |
| P2 | 新增数据源 | 不修改策略代码，只新增 adapter |

## 4. Domain and ownership model

### 4.1 核心领域

| 子域 | 类型 | 说明 |
|---|---|---|
| 策略研究 | Core | 产生 Alpha 的核心能力 |
| 回测引擎 | Core | 验证策略是否有研究价值 |
| 风控引擎 | Core | 决定系统能否安全实盘 |
| 订单管理 | Core | 管理委托、成交、撤单、状态机 |
| 账户核算 | Core | 资金、持仓、盈亏、对账 |
| 数据平台 | Supporting | 为策略提供可信数据 |
| 报告与绩效 | Supporting | 复盘、归因、展示 |
| 权限与审计 | Generic / Supporting | 安全与合规基础能力 |

### 4.2 关键实体

| 实体 | 说明 |
|---|---|
| Instrument | 股票、期货、ETF、币种等交易标的 |
| Bar / Tick | K 线或逐笔行情 |
| Factor | 因子值，如动量、估值、质量 |
| Signal | 策略产生的买卖意图 |
| TargetPosition | 目标仓位 |
| RiskCheckResult | 风控检查结果 |
| Order | 委托订单 |
| Execution | 成交回报 |
| Position | 持仓 |
| Account | 账户资金和权益 |
| StrategyRun | 一次策略运行实例 |
| BacktestRun | 一次回测实验 |
| DataVersion | 数据快照版本 |
| StrategyVersion | 策略代码和配置版本 |

### 4.3 重要不变量

| 不变量 | 所属上下文 | 说明 |
|---|---|---|
| 未通过风控的订单不能发送到券商 | 风控 / 订单 | P0 规则 |
| 同一个策略信号不能重复生成实盘订单 | 策略 / 订单 | 需要 idempotency key |
| 订单状态只能按合法状态机流转 | 订单管理 | 防止状态错乱 |
| 系统持仓必须可由成交流水重建 | 账户核算 | 便于审计和恢复 |
| 回测不能使用未来数据 | 回测 / 数据 | 防止研究失真 |
| 实盘状态以券商回报和对账为最终依据 | 订单 / 账户 | 本地状态不是绝对权威 |

## 5. Options and trade-offs

### 5.1 模块化单体 vs 微服务

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 模块化单体 | 简单、事务边界清晰、部署成本低、方便调试 | 模块边界需要纪律维护 | 推荐初期采用 |
| 微服务 | 独立扩缩容、团队边界清晰 | 分布式一致性、运维、链路追踪、部署复杂度高 | 暂不推荐 |
| 单脚本系统 | 开发最快 | 难审计、难恢复、难扩展、实盘风险高 | 只适合学习 demo |

推荐：**模块化单体**。用代码模块划清边界，不急着拆进程。

### 5.2 回测引擎：向量化 vs 事件驱动

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| 向量化回测 | 快、适合因子研究和大规模参数实验 | 难模拟订单、成交、资金、涨跌停 | 因子初筛 |
| 事件驱动回测 | 更接近实盘，可模拟订单和成交 | 慢、实现复杂 | 策略验证和实盘前测试 |

推荐：两层并存。

- 因子研究用向量化；
- 准备实盘的策略必须跑事件驱动回测。

### 5.3 存储选择

| 数据 | 推荐存储 | 理由 |
|---|---|---|
| 元数据 / 配置 / 订单 / 成交 | PostgreSQL | 事务、约束、查询、审计友好 |
| K 线 / 因子 / 回测结果明细 | Parquet + 对象存储 / 本地文件 | 便宜、列式、高压缩、适合批量分析 |
| 热点行情缓存 | Redis，可选 | 初期可不用，实时策略多了再加 |
| 日志 | 文件 + 日志系统 | 初期结构化日志即可 |

推荐：**PostgreSQL + Parquet**。先别上复杂数据湖。

### 5.4 同步调用 vs 事件队列

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 同步函数调用 | 简单、易调试 | 模块耦合较高 | 初期默认 |
| 本地任务队列 | 支持异步任务、重试 | 引入状态管理 | 数据同步 / 报告任务可用 |
| Kafka / Pulsar | 高吞吐、分布式 | 运维重，不必要 | Tick 级大规模再考虑 |

推荐：初期用同步调用 + 数据库任务表 / 轻量队列。不要过早 Kafka。

## 6. Recommended architecture

### 6.1 系统上下文

| 参与方 / 系统 | 关系 |
|---|---|
| 量化研究员 | 编写策略、运行回测、查看报告 |
| 交易员 / 操盘人 | 审核信号、启停策略、查看订单 |
| 风控负责人 | 配置仓位、回撤、标的黑名单等规则 |
| 数据源 | 提供行情、财务、宏观、公告数据 |
| 券商 / 交易所 API | 接收订单，返回成交和账户信息 |
| 通知系统 | 发送报警，如飞书、邮件、短信 |

### 6.2 容器 / 模块视图

```text
quant-system/
  data/
    ingestion          # 数据接入
    validation         # 数据校验
    storage            # 数据落库 / Parquet
    calendar           # 交易日历
  research/
    factor             # 因子计算
    notebook           # 研究实验
    dataset            # 训练 / 回测数据集
  strategy/
    interface          # 策略统一接口
    registry           # 策略注册和版本
    scheduler          # 策略调度
  backtest/
    vector_engine      # 向量化回测
    event_engine       # 事件驱动回测
    metrics            # 指标计算
  risk/
    pre_trade          # 事前风控
    intraday           # 事中风控
    post_trade         # 事后风控
  trading/
    oms                # 订单管理
    broker_adapter     # 券商适配
    execution          # 下单、撤单、状态同步
  portfolio/
    accounting         # 资金、持仓、盈亏
    reconciliation     # 对账
  ops/
    logging            # 结构化日志
    metrics            # 指标
    alerting           # 报警
    audit              # 审计
```

### 6.3 推荐部署

#### 阶段 1：单机 / 单服务器

```text
Python App
PostgreSQL
Parquet files
Cron / APScheduler
日志文件
```

适合研究、回测、模拟盘、小资金实盘。

#### 阶段 2：小型生产

```text
App Container x 2
PostgreSQL managed instance
Object Storage
Redis optional
Prometheus / Grafana
Alertmanager / 飞书通知
```

适合多策略、多账户、准实时交易。

#### 阶段 3：更高规模

```text
Data Workers
Strategy Workers
Risk Service
OMS Service
Market Data Service
Message Queue
Time-series / OLAP Store
```

触发条件：策略数量、团队边界、数据吞吐或可靠性隔离需要真正拆分。

## 7. Critical flows

### 7.1 数据接入流程

```text
数据源 → 拉取原始数据 → 原始区存储 → 校验 → 标准化 → 复权/对齐 → 发布数据版本 → 策略读取
```

关键控制：

- 原始数据不可覆盖；
- 清洗后数据带版本；
- 财务数据记录公告时间；
- 异常价格进入隔离区，不直接进入策略；
- 数据任务失败要报警。

### 7.2 回测流程

```text
选择策略版本
选择数据版本
选择参数
创建 BacktestRun
加载历史数据
逐 bar / tick 撮合
生成订单和成交
计算资金曲线
输出指标和报告
保存结果
```

关键控制：

- 回测结果必须绑定策略版本、数据版本、参数版本；
- 回测成交模型必须显式说明；
- 手续费、滑点、涨跌停、成交量限制必须可配置；
- 不允许策略读取未来数据。

### 7.3 实盘下单流程

```text
行情更新
策略生成目标仓位 / 信号
组合模块计算订单意图
事前风控检查
OMS 创建订单
Broker Adapter 发送订单
接收订单回报
接收成交回报
更新持仓和资金
触发日志、指标和报警
```

关键控制：

- 每个订单有 `client_order_id`，保证幂等；
- 风控拒绝时必须记录原因；
- 券商状态 unknown 时不能重复下单；
- 本地状态与券商日终对账；
- 支持全局一键停机。

### 7.4 日终对账流程

```text
拉取券商账户资金
拉取券商持仓
拉取券商成交
本地成交重建持仓
比较本地与券商差异
生成对账报告
差异超阈值报警
锁定相关策略或账户
```

## 8. Data, integration, and consistency model

### 8.1 数据分层

| 层级 | 内容 | 是否可变 |
|---|---|---|
| Raw | 原始数据源返回 | 不可变 |
| Clean | 清洗、类型转换、去重 | 可重算 |
| Adjusted | 复权、对齐、标准化 | 可重算 |
| Feature | 因子、特征、标签 | 可重算 |
| Result | 回测、模拟盘、实盘结果 | 不可随意改 |

### 8.2 订单状态机

```text
New → RiskRejected
New → Submitted → PartiallyFilled → Filled
Submitted → CancelRequested → Cancelled
Submitted → Rejected
Submitted → Unknown → Reconciled
```

原则：

- 状态只能向前流转；
- Unknown 状态必须靠券商查询或日终对账修复；
- 成交是持仓变化的唯一可靠来源；
- 撤单不代表没有成交，必须等待回报或对账。

### 8.3 一致性策略

| 场景 | 一致性策略 |
|---|---|
| 创建订单 | 本地事务写入订单，再发送券商；失败进入待确认状态 |
| 重复信号 | 使用 strategy_id + signal_time + instrument + side 生成幂等键 |
| 成交回报 | at-least-once 处理，按 execution_id 去重 |
| 持仓计算 | 可由成交流水重放重建 |
| 券商状态 | 券商为外部权威，本地通过对账修正 |
| 回测数据 | 使用固定数据版本，保证可复现 |

## 9. Security, reliability, observability, and operations

### 9.1 Security

| 风险 | 控制 |
|---|---|
| API Key 泄露 | 密钥加密存储，环境变量注入，不写入代码和日志 |
| 未授权下单 | 操作权限分级，实盘启停需要确认 |
| 错误策略实盘 | 策略必须经过回测、模拟盘和审批状态才可实盘 |
| 日志泄露 | 账户、Token、手机号、密钥脱敏 |
| 供应链风险 | 固定依赖版本，生产环境不随意升级 |

### 9.2 Reliability

| 场景 | 设计 |
|---|---|
| 数据源失败 | 重试 + 降级 + 使用上一可用数据版本，不盲目交易 |
| 券商 API 超时 | 有界重试，订单进入 Unknown，后续查询修复 |
| 策略异常 | 捕获异常，熔断单策略，报警 |
| 数据异常 | 价格跳变、成交量异常、空值校验，失败则隔离 |
| 系统重启 | 从数据库恢复策略运行、订单、持仓 |
| 极端行情 | 全局风险开关、最大回撤阈值、禁止开新仓 |

### 9.3 Observability

必须记录：

- 数据任务开始、结束、失败；
- 策略每次运行的输入数据版本；
- 信号生成原因；
- 风控检查结果；
- 订单创建、发送、回报、成交、撤单；
- 账户资金和持仓快照；
- 异常、重试、熔断、人工干预。

核心指标：

| 指标 | 用途 |
|---|---|
| data_delay_seconds | 数据延迟 |
| strategy_run_latency | 策略运行耗时 |
| signal_count | 信号数量 |
| risk_reject_count | 风控拒单数量 |
| order_submit_latency | 下单延迟 |
| order_unknown_count | 未知状态订单数量 |
| broker_error_count | 券商错误数量 |
| pnl_daily | 日收益 |
| max_drawdown | 最大回撤 |
| reconciliation_diff | 对账差异 |

### 9.4 Operations

上线前必须具备：

- 实盘和模拟盘环境隔离；
- 一键停止所有策略；
- 一键禁止开新仓；
- 券商断连后的恢复流程；
- 日终对账报告；
- 交易日志保存和导出；
- 策略版本回滚；
- 风控参数变更记录。

## 10. Capacity, cost, and delivery plan

### 10.1 初期容量假设

| 项目 | 初期目标 |
|---|---|
| 日线标的 | 10000 |
| 分钟线标的 | 1000 |
| 策略数量 | 20 |
| 单策略运行时间 | < 30 秒，日频；< 3 秒，分钟级 |
| 订单量 | < 1000 单 / 日 |
| 数据保留 | Raw 永久，清洗数据可重算，日志至少 1 年 |

这些目标用单机 PostgreSQL + Parquet 足够。不要为了这点规模提前上大数据平台。

### 10.2 成本模型

| 成本项 | 初期选择 |
|---|---|
| 计算 | 单台云服务器 / 本地工作站 |
| 数据库 | PostgreSQL |
| 文件 | 本地磁盘或对象存储 |
| 监控 | 开源 Prometheus / Grafana 或简单日志报警 |
| 数据源 | 先用免费 / 低成本源，实盘再买稳定数据 |
| 交易接口 | 券商 / 交易所官方 API |

### 10.3 分阶段交付

#### Phase 0：研究原型

交付：

- 数据下载脚本；
- 单策略回测；
- 指标报告；
- 最小目录结构。

验收：

- 能复现一个策略回测；
- 输出收益、回撤、夏普、交易明细；
- 数据版本和策略参数可记录。

#### Phase 1：可信回测平台

交付：

- 标准策略接口；
- 事件驱动回测；
- 成本和滑点模型；
- 数据校验；
- 回测结果持久化。

验收：

- 禁止未来函数；
- 同一配置可复现；
- 能跑样本外测试；
- 能导出报告。

#### Phase 2：模拟盘

交付：

- 实时 / 准实时数据接入；
- 模拟撮合；
- 策略调度；
- 风控检查；
- 持仓和资金模拟。

验收：

- 连续运行 20 个交易日；
- 无重复下单；
- 模拟持仓可由成交流水重建；
- 异常有报警。

#### Phase 3：小资金实盘

交付：

- Broker Adapter；
- OMS；
- 真实订单回报处理；
- 日终对账；
- 一键停机；
- 密钥管理。

验收：

- 小资金运行 1-3 个月；
- 对账差异为 0 或可解释；
- 无未处理 unknown 订单；
- 风控拒单可审计。

#### Phase 4：规模化

触发条件：

- 多账户；
- 多市场；
- Tick 数据；
- 多人协作；
- 订单量明显上升；
- 需要 7x24 稳定运行。

可能升级：

- 拆分 Market Data Service；
- 拆分 OMS / Risk Service；
- 引入队列；
- 引入容器编排；
- 引入时序数据库或 OLAP。

## 12. Risks, validation plan, ADRs, and next decisions

### 12.1 主要风险

| 风险 | 等级 | 应对 |
|---|---|---|
| 回测过拟合 | P0 | 样本外测试、滚动测试、参数敏感性分析 |
| 数据错误 | P0 | 数据校验、异常隔离、版本管理 |
| 重复下单 | P0 | 幂等键、订单状态机、重启恢复测试 |
| 券商状态不一致 | P0 | Unknown 状态、定时查询、日终对账 |
| 风控绕过 | P0 | 所有订单只能从风控后进入 OMS |
| 策略异常 | P1 | 单策略熔断、报警、隔离 |
| 交易成本低估 | P1 | 成本压力测试、滑点模型、实盘校准 |
| 容量不足 | P2 | 成交量约束、冲击成本模型 |

### 12.2 验证计划

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| 回测复现 | 同一配置重复运行 | 指标和交易明细一致 |
| 未来函数检查 | 构造延迟财报数据测试 | 策略不能读取未来数据 |
| 重启恢复 | 下单中途 kill 进程再恢复 | 不重复下单，状态可修复 |
| 风控拒单 | 构造超仓位订单 | 订单不发送券商，有拒绝日志 |
| 对账 | 模拟本地漏成交 | 对账发现差异并报警 |
| 成本敏感性 | 手续费 / 滑点上调 2-5 倍 | 策略仍有合理安全边际才可继续 |
| 模拟盘 | 连续运行 20 个交易日 | 无状态错乱、无未解释差异 |

## 13. Decision rationale and validation evidence

### 13.1 为什么不是微服务

当前假设下，系统主要瓶颈不是单服务吞吐，而是：

- 数据正确性；
- 策略可复现；
- 风控前置；
- 订单状态一致性；
- 实盘可恢复。

微服务会提前引入：

- 分布式事务；
- 服务发现；
- 链路追踪；
- 消息重复消费；
- 运维复杂度。

这些复杂度不能提高早期 Alpha 研究质量，反而增加实盘风险。

### 13.2 为什么 PostgreSQL + Parquet

PostgreSQL 适合：

- 订单；
- 成交；
- 持仓；
- 配置；
- 审计；
- 状态机。

Parquet 适合：

- 大量 K 线；
- 因子矩阵；
- 回测明细；
- 批量读取和压缩存储。

这比一开始引入复杂数据湖更简单，也足够支撑中低频量化。

### 13.3 为什么回测和实盘要共用策略接口

如果回测一套代码、实盘另一套代码，就会出现：

- 回测成交逻辑和实盘不一致；
- 信号生成时点不一致；
- 风控规则不一致；
- 参数解释不一致。

因此策略接口必须统一：

```text
on_data(data) -> target_position / orders
```

同一策略在不同 runtime 中运行：

```text
BacktestRuntime
PaperTradingRuntime
LiveTradingRuntime
```

这样能最大限度减少“研究到实盘”的偏差。
